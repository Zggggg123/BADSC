# BADS3 协议与维护

## 外层

**分享码**是完整的 `卡组名-内容码`。以最后一个 `-` 分隔，所以卡组名自身可以包含连字符。内容码使用无填充 Base64URL，但把其中的 `-` 映射为 `.`，避免与分隔符冲突。卡组名保持可读，且不放入压缩负载。内容码解出的字节依次为：

1. 1 字节内部压缩格式版本：`2` 或 `3`。
2. 1 字节卡组名类型：`0` 为文本，`1` 为 `null`（可见名称为空）。
3. 原 `.dek` 的 16 字节 IV。
4. 若版本为 `3`，接 8 字节字典 ID（快照文件 SHA-256 的前 8 字节）和 1 字节模式：0 行式二进制、1 行式二进制+Brotli、2 列式二进制、3 列式二进制+Brotli。
5. 若版本为 `2`，接 1 字节模式：0 为结构化数据+Brotli，2 为保留原始 JSON 排版的去名数据+Brotli。
6. 对应模式的负载。
7. `UTF-8(可见卡组名) + 前面所有编码字节` 的 SHA-256 前 8 字节校验。

完整分享码最多 2 Mi 字符；解压后的二进制最多 2 MiB；还原的 `.dek` 最多 1 MiB。字典文件最多 512 KiB。读取器还对文本、卡片、改装和列数据设独立上限。解码先核对包含可见名称的校验，再按字典 ID 读取 `dictionaries/manifest.json` 中**指定**的快照及完整 SHA-256，绝不替换成 `current`。ID 与校验是格式完整性手段，不提供密码学签名。旧 `BADS2:` / `BADS3:` 前缀码不再导入。

## 内层

行式负载以 varuint `1` 开始；列式以 `2` 开始。两者使用无符号 varuint、zigzag 有符号整数和 UTF-8 字符串池。行式按卡片写字段，列式将同种字段聚为 24 列，分别选择 varuint、最小值/GCD 位打包或相邻差分中最短的表示。字段顺序由代码中的固定 schema 定义，改装的 `run`、`cwun` 使用字符串池索引，`0` 表示 `null`，空字符串有独立索引。两种模式都对单卡组内重复改装建池。

字典条目为 `[modId,optId,cost,run,cwun]`，按 `(modId,optId)` 升序唯一排列。改装池中的引用 `0` 表示完整记录，正数 `n` 表示字典第 `n-1` 项。命中项随后带 6 位字段差异掩码；未命中时行式直接保存六字段，列式使用掩码 `63` 保存六字段。第六字段 `.dek.type` 的字典默认值为 `0`，非零值或其他不匹配值必须以差异覆盖。两种改装列表都编码。旧卡组的价格、名称、`null`/空串差异一律以原文件为准。

只有解析后的卡组 JSON 完全符合已知 schema、且重建的明文字节与输入相等时才采用 BADS3；否则使用 BADS2。两种格式都在压缩前移除 `name`。未知结构或排版由 BADS2 的原始 JSON 去名模式保存，恢复时将外部名称写回同一位置。若原始名称字段无法无损外置，生成器报错。最终比较包含可见名称、内部版本、IV、字典 ID 与校验在内的完整分享码长度。`.dek` 加密后会保留原 IV，所以明文字节相同即可逐字节还原密文。

## 快照生命周期

`web/dictionaries/*.json` 由仓库 `.gitattributes` 禁止 Git 换行符转换，必须保留原始字节，否则内容 SHA-256 校验会失败。Windows 新检出和线上 Linux 发布均须遵守此规则。

`tools/build-dictionary.cjs` 仅读 JSON 数据，不执行提取器。它从 BA-Units `Options.json` 读取五项字段，附上来源版本、日期、源文件哈希、生成格式版本，再确定性序列化。快照文件名就是内容 SHA-256 前 16 个十六进制字符；清单另存完整 SHA-256。若同名文件已有不同内容或源 JSON 无效，生成器报错且不覆盖已发布快照。发布新版时把清单和已生成分享码引用的历史快照一起部署；原始 `Options.json` 不需要部署。当前公开来源的元数据只是来源标记，不能当作游戏最新版本或兼容性结论。
